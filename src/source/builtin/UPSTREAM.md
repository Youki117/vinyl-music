## 为什么内置一份

之前的做法是让用户自己去导入音源脚本 —— 洛雪就是这样，但对我们不合适：

1. 用户手上那几份（野草 / 野花 / 六音 / Huibq）**在 2026-08-19 已全部失效**，
   服务端分别返回 404 / 403 / 503。指望用户自己找到一份能用的，等于这个功能不存在。
2. 音源脚本的寿命以周计。内置一份能用的，至少保证装上就能听；
   失效之后仍可以用「导入音源」覆盖，两条路并存。

**这不改变信任模型**：内置的脚本和用户导入的脚本走完全同一条路 —— 丢进 Worker 里跑，
没有 DOM、没有 window、没有 Tauri IPC，网络请求由主线程代发。详见 `../userApi/protocol.ts`。

## 它需要宿主提供什么

只有 `globalThis.lx` 的 `EVENT_NAMES` / `request` / `on` / `send` 四个，
**不碰 `lx.utils`**（不需要 crypto、zlib、buffer）。所以它对宿主的要求比野草那类脚本低得多。

## 已知的毛病（不修，改了就没法跟上游对 diff）

- 脚本里 `HUIBQ_API` / `LINGCHUAN_API` 两条链路是占位地址，密钥写着 `your_key_here`，
  必然失败。它自己有多链路回退，失败只是多花几百毫秒，不影响结果。
- 酷狗有时会回落到 `music.haitangw.cc` 的地址，那个地址返回 JSON 而不是音频。
  所以 `src/source/index.ts` 的 `resolvePlayUrl` 会再做一次跨平台换源。

## 换一份音源

把新脚本覆盖到 `qdy.js`，更新上面的 md5，然后：

```
node scripts/probe-source.mjs src/source/builtin/qdy.js
```

跑通再提交。这个脚本不经过本应用，能把「音源自己挂了」和「我们接错了」分开。
