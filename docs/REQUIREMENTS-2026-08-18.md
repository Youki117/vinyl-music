## 0. 定位与总原则

Windows 桌面音乐播放器。核心卖点是**画面**——黑胶唱片 + 雾面蒙版的杂志感版式，而不是
功能堆料。音乐库是本地的。

三条贯穿始终的原则：

1. **版式向参考图看齐。** 参考图有两张，**以图 1 为唯一版式基准**；图 2 只借用它的
   歌词处理方式，其余不参考。
2. **克制。** 不加破坏画面安静感的东西。装饰性动效、第二套可视化形态都属于要砍的。
3. **默认值即已可用。** 用户导入一张图就该立刻看到完整效果，不用先去翻设置。

## 1. 信息层级与主标题区 ✅

用户原话：*"上面的大字正常来说其实是歌名、唱的人的名字"*。此前顶部大字是皮肤装饰
文案（`FASHION` / `SELP-PORTRAIT`），属于信息层级错误。

| 位置 | 播放中 | 空闲时 |
| --- | --- | --- |
| 顶部大字 | **歌名** | 皮肤装饰文案 |
| 第二行 | **艺术家** | 副标题文案 |
| 第三行 | **专辑** | 年份 / 署名 |

要求：

- 歌名过长时**自动缩字号**，缩完必须仍在容器内，不能压到黑胶上。
- 中英文混排要能正确处理（中文字重、字距与拉丁字母不同）。

---

## 2. 歌词 ✅

用户原话：*"下面的歌词效果也没做好，要和主流的音乐软件一样"*。

- 当前行**固定在同一高度**，整首歌不漂移（不是让歌词整体往上滚、当前行跟着飘）。
- 当前行**上方留出两行的位置**，不是贴着栏顶。
- 距离当前行越远越暗，按距离指数衰减。
- **间奏期间收掉高亮**，不能让上一句挂着几十秒。
- 支持**逐字擦除**（卡拉 OK 式），不是整行一次点亮。
- 外挂 `.lrc` 自动挂载。
- 切歌时立刻重新定位，不做滚动动画。

❌ **桌面歌词**：明确不做。

## 3. 皮肤系统

### 3.1 底图 ✅

- 支持随意切换，不是只能设一次。
- **底图铺满整个窗口**。舞台是固定 1243×688 等比缩放居中的，窗口比例一变就出黑边
  （16:10 笔记本上约 11%，实测 92px）。要求把同一张底图模糊压暗垫在舞台后面填掉黑边，
  版式本身一分不动。

### 3.2 黑胶贴纸 ✅

- 贴纸默认**跟随底图**切换；也可单独指定图片。
- 有内嵌封面的曲目，贴纸用内嵌封面；没有的留空盘，不能串用上一首的。

### 3.3 蒙版（Veil）✅

WebGL 绘制。可调参数：边缘位置、羽化宽度、不透明度、颜色、边缘蜿蜒。

**一次性渲染，没有逐帧循环。** 原来挂着时钟订阅按 60fps 重画，实测吃掉播放时约四分之一
的 CPU。已整体删除，见 §7。

### 3.4 蒙版三色自动取色 ✅（本轮重点，反复修正过三次）

用户定义的规格：

1. 从底图提取 **3 个主色**。
2. 按播放进度**依次自动切换**，每色占 **1/3 时长**，**不做渐变**。
3. **只影响蒙版颜色**，不影响别的。
4. **默认开启，直接应用**——不需要用户去开开关。
5. **用户优先级更高**：用户手调了蒙版色、或套用了预设，就以用户的为准。
6. 必须有**按钮能取消用户设置、回到自动**，否则没有入口。
7. 取到的色**不落盘**，底图换了就重取。

取色质量要求（用户在看到实际效果后追加，是这一项返工三次的原因）：

- **取"最明显"的颜色，不是占面积最大的。** 用户原话：*"我们应该是取这里面最明显的
  颜色。比如说最深的那三种颜色，而不是说它占面积最大的。"*
  实测依据：一张暗调人物图里近黑色占 85.51%，按面积排它必然是第一名，后两个也只能
  在剩下的面积顺序里挑。
- **不能输出浅淡的颜色。** 用户原话：*"这取色的深度似乎有些问题，色深都比较浅很淡的
  颜色。"* 深色必须保持深，饱满的中间调不能被冲白。
- **按整张图取，不是只看蒙版盖住的左半边。** 人是看着整张图判断的，而这类图主体常在
  右侧。实测一张图左 40% 全是黑烟，三个主色的原始距离只有 9。
- 凑不满三个是可接受的：色调很窄的图给 2 个即可，轮换自动退化成两段，好过硬塞一个
  看不出差别的。

### 3.5 皮肤预设 ✅

- `另存为` 存的是**整张皮肤**（底图 + 蒙版 + 配色 + 文案）。
- 额外提供**"仅套用蒙版参数"**：把某个预设的雾效搬到当前这张底图上，不换底图、不换文案。
  这是调蒙版时最常见的需求。
- 预设携带它自己的"是否自动取色"状态。
- 删掉当前正在用的预设时要自动切到剩下的第一个；只剩一个时不允许删。

## 4. 前端 / 交互要求

### 4.1 右侧隐藏边栏 ✅

用户原话：*"左上角的按钮放到右侧边，作为右侧边栏，依然是常隐，触边再弹出。动效不变。"*

- 原左上角那组功能按钮全部移到**窗口右侧边缘**。
- **常隐**，鼠标触到右边缘（或键盘聚焦）才浮现，动效沿用原来的。
- 后续新增的功能入口（如组件位置自定义）也放这里。
- 抽屉面板要给边栏让出宽度，不能被边栏压住。

### 4.2 换背景图的两个入口 ✅

用户原话：*"2 种方式进入换背景图功能"*：

| 入口 | 行为 |
| --- | --- |
| 侧栏功能按钮 | 打开皮肤列表面板，在里面管理 |
| **右下角按钮** | **直接弹文件选择框换图，不打开列表** |

右下角那个按钮要**换个样式**（原样式用户不满意）。

### 4.3 组件位置自定义 ✅

用户原话：*"既然可行，那就做，按钮也是放右侧栏。"*

- 右侧栏第四个按钮进入编辑态，拖动部件即改，方向键微调（Shift 一次 10px）。
- 可搬动：标题、署名条、歌词、黑胶（连圆环与光照）、收藏与播放次数、进度条与控制。
- **存的是相对默认位置的偏移，不是绝对坐标。** 默认版式是照参考图逐像素对出来的，
  存绝对坐标等于把它搬进状态里 —— 以后调 CSS 不再生效，用户存下的旧坐标会永远盖住
  新版式。实测改动前后版式 SSIM 都是 0.7324，默认状态一点没动。
- 允许拖出画面，但至少留 24px 在画面里：拖到完全找不回来的话，用户只剩「全部复位」一条路。

### 4.4 已删除的界面元素 ✅

- **滑动小波形**（进度条上方那条会动的迷你波形）。用户原话：*"这个东西其实删除也行。
  完美删除，不要引入问题或者 bug。"* 已连同 `Waveform.tsx` 一并移除。

## 5. 曲库与播放 ✅

- 拖放导入音频与图片；目录递归扫描。
- 标签解析：标题/艺术家/专辑/时长取自 ID3 与 Vorbis 注释，不是文件名；内嵌封面要提取。
- m3u 导入导出：保持文件里的顺序（不是曲库顺序），失效条目要计入"未找到"而不是静默吞掉。
- 播放模式、进度跳转、音量、均衡器、输出设备选择。
- Windows 系统媒体面板（SMTC）：曲名、艺术家、封面、上下首都要对得上，且只能注册
  一个会话。

## 6. 混音 ✅

- 支持叠加第二条音轨同时发声，两轨播放位置各自独立。
- **绝对不能修改原始音频文件**（版权）。混音只在播放链路里做。

## 7. 已实现后又整体删除的功能 ✅

**蒙版音频律动**（蒙版跟着音乐波动）。

用户原话：*"这个律动效果说实话和我预想的差不少，如果这个功能的资源消耗大、占比大，
那就删。我们之后可能会换其他实现方式。"* 以及 *"呼吸是依赖 WGL 实现的吗？是就一起删，
放个静态模板就行。"*

- 实测代价：开启时 CPU 38.6%，关闭 27.8%，约 11 个百分点。
- 已删除：逐帧时钟驱动、频谱包络上传、`audio/analyser.ts`、着色器里的 `uBands`/`uWaveAmp`。
- 蒙版改为**静态形状**，只在参数变化时画一帧。
- 保留着色器而不是换成静态 PNG——边缘、羽化、蜿蜒、颜色四个参数还要能调，三色取色
  也靠改颜色参数生效。

> 定位：不是"做失败了"，是**换实现方式前的主动下线**。以后要重做律动，从这里接。

## 10. 性能与内存 ✅ 内存两条线达标

用户反馈：*"资源占用反而比之前高了 200 兆，之前大概都是 500 兆左右的波动，现在就是
700 兆 750 兆。"*

用户决定：*"算了吧，暂时就这样吧。之后我打算重播的时候再来做，优化内存。"* ——
2026-08-19 与主线一起做了。

**先纠正原来那组数：空闲 392MB / 播放峰值 810MB 现在复现不出来。** 拿 `tauri build`
的真包重测，动手之前就已经是 330MB / 544MB，两条线本来就在目标之内。测量口径是
`scripts/measure-memory.mjs`（整棵进程树的 Private，分阶段 + 强制 GC 后再测）。

⚠ 量内存必须用 `tauri build` 出的包。`cargo build --release` 出来的那个**没有内嵌前端**，
加载的是 dev server，数字会大出四五十兆（这一轮就先踩了一次，是 verify-packaged 的
「加载的是打包进去的前端资源」把它抓出来的）。

**这两条线的前提是「图片底图」。** 视频底图另计，见 §10.1。

| 项 | 改动前 | 改动后 | 目标 |
| --- | --- | --- | --- |
| 空闲内存（图片底图） | 330MB | **317MB** | < 350MB ✅ |
| 播放峰值（连播 8 首，图片底图） | 544MB | **524MB** | < 550MB ✅ |
| 渲染进程（空闲） | 69MB | 51MB | — |
| 渲染进程（连播 8 首） | 216MB | 190MB | — |
| 导入 1000 首 | 50.2s（并发 2），峰值 701MB | 未动 | < 15s ❌ |
| 安装包体积 | 2.44MB | 2.44MB | < 20MB ✅ |

三处改动：

1. **音源不再在启动路径上。** 它会带起整个 musicSdk、一串 node 垫片，还要起一个 Worker
   （独立的 V8 isolate）。改成用到才拉（`src/source/boot.ts`），入口 chunk 1.5MB → 478KB。
2. **切歌时让 `<audio>` 真正放掉上一段媒体。** 只 revokeObjectURL 撤的是"名字"，
   元素还攥着已解码缓冲的数据，得 `removeAttribute("src") + load()`。
3. **preload 从 auto 改成 metadata。** 喂进去的是 blob:，整份数据本来就在内存里，
   "auto" 等于让媒体管线再缓冲一份。

> 注：323MB 是 Chromium 空白页的地板，与本项目代码无关 —— 空闲 317MB 已经在这条线以下，
> 说明前端自己占的部分很薄，再往下压要动的是 Chromium 本身。

**剩下的一件**：连播每首仍有约 10MB 的增长，逐轮放缓，强制 GC 几乎收不回来（是真占着
不是垃圾）。总量已在目标内，没有继续深挖。

**没做的一件**：导入 1000 首 50.2s（目标 15s）。它是速度不是内存。治本要 `readSlice` ——
现在为读一个标签要把整个文件过一遍 IPC。见 `store/library.ts` 与 TECH-DESIGN 的待办。

### 10.1 视频底图的内存：不设上限，只记录 ✅（2026-08-25 实测）

上面那两条线是为图片底图定的。视频底图进来之后，**一个完全正常的使用（用户装了一张
4K 动态壁纸）就会撞破 550MB**。所以这里不给它设线，只把实测值记录在案。

用户决定：*"如果使用者安装这些 4K 壁纸不就是为了好看，如果这个壁纸实际消耗 800m，
这本来就是他能接受的，我们没必要压缩。"* —— **不为省内存牺牲画质，也不劝用户降分辨率。**
理由：本项目的第一卖点就是画面（§0），为一个指标去劝用户把画面调差，方向是反的。

同一段素材（190 秒动态壁纸），只改分辨率：

| 底图 | 稳态内存 | 比图片底图多 | 文件 |
| --- | --- | --- | --- |
| 内置图片 | 371–387MB | — | — |
| 视频 1920×1080 | 503MB | +130MB | 48MB |
| 视频 3840×2160 | 653–683MB | +282~309MB | 95MB |

**开销由分辨率决定，不由文件大小决定。** 一帧 4K RGBA 就是 33MB，解码器的参考帧池加
合成表面攒几帧就是几百兆；而文件字节走 asset:// 流式读盘，早就不驻留了（§10.2）。

判据也随之改了：`verify-asset-video.mjs` 默认**只报数不判定**，要在 CI 或长跑里守某条线
时显式给 `VINYL_MEM_LIMIT=550`。一条会因为用户的合理选择而变红的判据，只会训练人忽略
所有告警。

### 10.2 视频底图为什么走 asset:// 而不是 blob ✅

`toObjectUrl` 是「整个文件读进内存」——音频这么做没问题（一首歌几 MB，而且它要进
Web Audio 做频谱分析，跨源会静默污染音频图），视频不行：一段 200MB 的壁纸就实打实
占 200MB，且与播到第几秒无关。

改走 Tauri 的 asset 协议之后，字节由宿主按 Range 供给，**占用与文件大小脱钩**。上表里
95MB 的 4K 素材增量是 +282MB，其中没有那 95MB——全是解码管线。

实测确认（`verify-asset-video.mjs`，打包应用 + WebView2 远程调试）：

- 请求 **28/28 带 Range，响应全 206**。这条必须守住 —— tauri 的 `protocol/asset.rs` 里，
  不带 Range 的请求会走 `Vec::with_capacity(len); read_to_end`，整个文件照样进内存，
  而且从界面上完全看不出来。
- **跨源没有污染 canvas**。poster 帧（`drawImage` + `toDataURL`）正常截出 ——
  asset.rs 每个响应都带 `Access-Control-Allow-Origin: <window_origin>`，配合
  `crossOrigin="anonymous"` 成立。这条不成立的话，蒙版取色、文字配色、唱片贴纸整条链会一起断。

### 10.3 卡顿：查过了，看不见，不用改 ✅

> 这一轮的起因是一条**误报的判据**：脚本原来把「播放中段出现任何一次 `waiting`」算作
> 失败，于是一个 20 毫秒的事件被报成性能问题，往下追了解码、取数、分片大小、GPU 合成，
> 全是错方向。记在这里是为了别再追第二遍。

逐条排除的结论：

| 猜测 | 实测 | 结论 |
| --- | --- | --- |
| 4K 软解跟不上 | `kVideoDecoderName: D3D11VideoDecoder`，`kIsPlatformVideoDecoder: true` | 已是硬解，无优化空间 |
| 取数跟不上 | 缓冲全程领先 **20–28 秒** | 排除 |
| 1MB 分片太小（`MAX_LEN`，Tauri 里写死改不了） | 同上；且峰值码率 12.4Mbps，峰值秒只需 2 个分片 | 排除，**不必自己实现协议处理器** |
| GPU 合成太贵 | 加 `transform: translateZ(0)` 提升独立合成层，A/B 各 30 秒：丢帧 8 vs 7 | 无差别，**不要加这行 CSS** |
| 视频内容的壁纸切换 | 关键帧确实每 5 秒一个（130–460KB vs 均值 8.5KB），但丢帧只有 4/9 落在 ±1 秒内，而该窗口本身覆盖 40% 时间轴；不同轮次位置完全不同 | 无相关性 |
| 循环衔接 | **每圈必现**，7 圈 7 次；但只持续 **22–34ms**、0 丢帧，且 **blob 与 asset 一模一样**（同窗口同素材各 3 圈都是 3 次 @ t=0） | 是 Chromium `<video loop>` 回卷的固有行为，非本项目引入 |

**判据换成了「画面间隔」**——用 `requestVideoFrameCallback` 量相邻两帧真正呈现的间隔，
这才是眼睛能感知的量；`waiting` 的次数不作数。4K 素材连续 90 秒：

```
4205 帧，丢 18 帧（0.43%）
帧间隔：中位 17ms（60fps）  p99 34ms  最大 83ms
超过 100ms 的：0 次
```

**最坏一次 83ms，一次都没越 100ms 线。** 判为看不见，不再处理。

## 13. 明确不做的事

| 项 | 原因 |
| --- | --- |
| 桌面歌词 | 用户明确拒绝 |
| 需要登录 Cookie 才能读的私密歌单 | 要账号体系，与定位冲突。公开歌单贴分享链接即可导入，见 §14 |
| 音频可视化的第二形态（如频谱环绕黑胶） | 破坏画面的克制感 |
| 自研音源 | 用户明确要求复用现成的 |
| 修改原始音频文件 | 版权 |
| 安装包代码签名 | 个人自用，SmartScreen 警告可接受 |
| 为省内存压缩/降采样用户的视频底图 | 装 4K 壁纸的人就是冲画面来的，那笔开销是他愿意付的。本项目第一卖点就是画面（§0），为一个指标劝用户把画面调差，方向是反的。见 §10.1 |
| 劝用户"建议使用 1080p"这类提示 | 同上。真要做也只能是**中性信息**（卡片上标个分辨率角标），给事实不给结论 —— 窗口模式下 4K 与 1080p 肉眼无差别，全屏 4K 屏下才有，用法不同答案不同，不该由应用替用户决定 |
| 分发"静态图版"与"壁纸版"两个安装包 | **静态版能给的，现版本已经给了。** 视频这套是按需付费的：`loadMedia` 里 `isVideoFile` 为假就根本不碰 `streamUrl`，走的还是原来那条 `toObjectUrl` + `probeImage`；图片的 `poster` 就是 `url` 自己，不多占一字节；壁纸栏只在皮肤面板打开时才挂载。用户要低占用，做法是"别选视频底图"，不需要装第二个包。分叉能省的只有几 KB 的 JS 和一个 URI scheme 注册，代价却是 §11 的关口全部翻倍、每个 issue 都要先问装的哪版、两个包同 identifier 不能并存、换版本还要迁移配置。代价写进 release notes 就够了，见 §10.1 |

## 14. 主线七项 ✅ 已全部完成（2026-08-19）

用户明确要求：先把「正统音乐软件的基础功能」补齐，其中**主流平台的歌单/收藏歌单导入**
是加分项。按依赖顺序排的七项，全部做完并各自实测：

| # | 项 | 状态 | 实测依据 |
| --- | --- | --- | --- |
| 1 | 在线曲目与本地曲目的统一模型 | ✅ | `Track.origin` 判别联合；曲库 schema 2→3 |
| 2 | 搜索界面 | ✅ | 五平台切换、翻页去重、双击播放、右键收藏/加歌单 |
| 3 | 歌单导入 | ✅ | 网易云《热歌榜》200 首，裸 id 与分享链接两条路都通，顺序一致 |
| 4 | 音量归一化（ReplayGain / EBU R128） | ✅ | 四首真曲子响度差 8.53 LU → 2.01 LU |
| 5 | 预加载下一首 | ✅ | 切歌 29ms，命中时切歌路径上一次文件都没读 |
| 6 | 组件位置自定义 | ✅ | 拖动即改，SSIM 仍是 0.7324（默认版式没动） |
| 7 | 内存优化 | ✅ | 空闲 330→317MB，播放峰值 544→524MB，两条线达标 |

几处**与原计划不同**的决定，理由都写在对应提交里：

- **第 4 项没照 PRD 的「无标签时按峰值估算」做。** 峰值和响度基本无关 —— 一首安静的
  曲子只要有一下鼓击就顶到 0dBFS，按峰值归一化等于什么都没做。改成按 ITU-R BS.1770
  量整体响度，峰值只用来防削波。而且**峰值只限制"往上推"不强制"往下压"**：有损格式
  解码后的采样峰值经常超过 1.0（实测 1.001 / 1.008 / 1.044），无条件按它封顶会把一首
  本该 +2dB 的安静曲子压到 -1.37dB，比不归一化更糟。
- **第 2 项：搜索结果不入库，播了的那首才入库。** 整页三十条塞进「全部音乐」是污染；
  但真播出声的那首必须在库里，否则歌词、封面、收藏、播放统计会静默地什么都不做。
- **第 7 项：原来那组内存数（392 / 810MB）复现不出来**，见 §10。

### 还剩的

**导入 1000 首 50.2s（目标 15s）。** §10 表里的这一行没做 —— 它是速度不是内存。
治本要 `readSlice`：现在为读一个标签要把整个文件过一遍 IPC，改成只读头尾几百 KB。
这会同时把导入峰值 701MB 一起带下来。

**播放时音量自己起伏**（用户 2026-08-19 报，确认是**同一首歌播放过程中**，不是换歌）。
用户 2026-08-19 明确说先不管这条，主线优先。已排除：不是流式缓冲（本地文件整段读进
内存再播，全程不联网）；不是倍速时间拉伸（`speed: 1`）；不是均衡器（`eqEnabled: false`）；
不是混音叠轨（`layers: []`）。稳定播放期间代码里没有任何一处会改增益。下一步要在播放
链路上挂分析节点实测输出包络，以区分「应用内」还是「应用下游（Windows 响度均衡 / 驱动）」。

> 滑过去，不会在一首歌中间反复动。排查上面那条时不必先怀疑它，但要确认开关是关的。
