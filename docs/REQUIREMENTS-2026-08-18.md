## 0. 定位与总原则

Windows 桌面音乐播放器。核心卖点是**画面**——黑胶唱片 + 雾面蒙版的杂志感版式，而不是
功能堆料。音乐库是本地的。

三条贯穿始终的原则：

1. **版式向参考图看齐。** 参考图有两张，**以图 1 为唯一版式基准**；图 2 只借用它的
   歌词处理方式，其余不参考。
2. **克制。** 不加破坏画面安静感的东西。装饰性动效、第二套可视化形态都属于要砍的。
3. **默认值即已可用。** 用户导入一张图就该立刻看到完整效果，不用先去翻设置。

## 1. 信息层级与主标题区 ✅

用户原话：*"上面的大字正常来说其实是歌名、唱的人的名字"*。此前顶部大字是皮肤装饰
文案（`FASHION` / `SELP-PORTRAIT`），属于信息层级错误。

| 位置 | 播放中 | 空闲时 |
| --- | --- | --- |
| 顶部大字 | **歌名** | 皮肤装饰文案 |
| 第二行 | **艺术家** | 副标题文案 |
| 第三行 | **专辑** | 年份 / 署名 |

要求：

- 歌名过长时**自动缩字号**，缩完必须仍在容器内，不能压到黑胶上。
- 中英文混排要能正确处理（中文字重、字距与拉丁字母不同）。

---

## 2. 歌词 ✅

用户原话：*"下面的歌词效果也没做好，要和主流的音乐软件一样"*。

- 当前行**固定在同一高度**，整首歌不漂移（不是让歌词整体往上滚、当前行跟着飘）。
- 当前行**上方留出两行的位置**，不是贴着栏顶。
- 距离当前行越远越暗，按距离指数衰减。
- **间奏期间收掉高亮**，不能让上一句挂着几十秒。
- 支持**逐字擦除**（卡拉 OK 式），不是整行一次点亮。
- 外挂 `.lrc` 自动挂载。
- 切歌时立刻重新定位，不做滚动动画。

❌ **桌面歌词**：明确不做。

## 3. 皮肤系统

### 3.1 底图 ✅

- 支持随意切换，不是只能设一次。
- **底图铺满整个窗口**。舞台是固定 1243×688 等比缩放居中的，窗口比例一变就出黑边
  （16:10 笔记本上约 11%，实测 92px）。要求把同一张底图模糊压暗垫在舞台后面填掉黑边，
  版式本身一分不动。

### 3.2 黑胶贴纸 ✅

- 贴纸默认**跟随底图**切换；也可单独指定图片。
- 有内嵌封面的曲目，贴纸用内嵌封面；没有的留空盘，不能串用上一首的。

### 3.3 蒙版（Veil）✅

WebGL 绘制。可调参数：边缘位置、羽化宽度、不透明度、颜色、边缘蜿蜒。

**一次性渲染，没有逐帧循环。** 原来挂着时钟订阅按 60fps 重画，实测吃掉播放时约四分之一
的 CPU。已整体删除，见 §7。

### 3.4 蒙版三色自动取色 ✅（本轮重点，反复修正过三次）

用户定义的规格：

1. 从底图提取 **3 个主色**。
2. 按播放进度**依次自动切换**，每色占 **1/3 时长**，**不做渐变**。
3. **只影响蒙版颜色**，不影响别的。
4. **默认开启，直接应用**——不需要用户去开开关。
5. **用户优先级更高**：用户手调了蒙版色、或套用了预设，就以用户的为准。
6. 必须有**按钮能取消用户设置、回到自动**，否则没有入口。
7. 取到的色**不落盘**，底图换了就重取。

取色质量要求（用户在看到实际效果后追加，是这一项返工三次的原因）：

- **取"最明显"的颜色，不是占面积最大的。** 用户原话：*"我们应该是取这里面最明显的
  颜色。比如说最深的那三种颜色，而不是说它占面积最大的。"*
  实测依据：一张暗调人物图里近黑色占 85.51%，按面积排它必然是第一名，后两个也只能
  在剩下的面积顺序里挑。
- **不能输出浅淡的颜色。** 用户原话：*"这取色的深度似乎有些问题，色深都比较浅很淡的
  颜色。"* 深色必须保持深，饱满的中间调不能被冲白。
- **按整张图取，不是只看蒙版盖住的左半边。** 人是看着整张图判断的，而这类图主体常在
  右侧。实测一张图左 40% 全是黑烟，三个主色的原始距离只有 9。
- 凑不满三个是可接受的：色调很窄的图给 2 个即可，轮换自动退化成两段，好过硬塞一个
  看不出差别的。

### 3.5 皮肤预设 ✅

- `另存为` 存的是**整张皮肤**（底图 + 蒙版 + 配色 + 文案）。
- 额外提供**"仅套用蒙版参数"**：把某个预设的雾效搬到当前这张底图上，不换底图、不换文案。
  这是调蒙版时最常见的需求。
- 预设携带它自己的"是否自动取色"状态。
- 删掉当前正在用的预设时要自动切到剩下的第一个；只剩一个时不允许删。

## 4. 前端 / 交互要求

### 4.1 右侧隐藏边栏 ✅

用户原话：*"左上角的按钮放到右侧边，作为右侧边栏，依然是常隐，触边再弹出。动效不变。"*

- 原左上角那组功能按钮全部移到**窗口右侧边缘**。
- **常隐**，鼠标触到右边缘（或键盘聚焦）才浮现，动效沿用原来的。
- 后续新增的功能入口（如组件位置自定义）也放这里。
- 抽屉面板要给边栏让出宽度，不能被边栏压住。

### 4.2 换背景图的两个入口 ✅

用户原话：*"2 种方式进入换背景图功能"*：

| 入口 | 行为 |
| --- | --- |
| 侧栏功能按钮 | 打开皮肤列表面板，在里面管理 |
| **右下角按钮** | **直接弹文件选择框换图，不打开列表** |

右下角那个按钮要**换个样式**（原样式用户不满意）。

### 4.3 组件位置自定义 🚧

用户原话：*"既然可行，那就做，按钮也是放右侧栏。"*

- 允许用户调整界面组件的位置。
- 入口按钮放右侧边栏。
- **尚未开始。**

### 4.4 已删除的界面元素 ✅

- **滑动小波形**（进度条上方那条会动的迷你波形）。用户原话：*"这个东西其实删除也行。
  完美删除，不要引入问题或者 bug。"* 已连同 `Waveform.tsx` 一并移除。

## 5. 曲库与播放 ✅

- 拖放导入音频与图片；目录递归扫描。
- 标签解析：标题/艺术家/专辑/时长取自 ID3 与 Vorbis 注释，不是文件名；内嵌封面要提取。
- m3u 导入导出：保持文件里的顺序（不是曲库顺序），失效条目要计入"未找到"而不是静默吞掉。
- 播放模式、进度跳转、音量、均衡器、输出设备选择。
- Windows 系统媒体面板（SMTC）：曲名、艺术家、封面、上下首都要对得上，且只能注册
  一个会话。

---

## 6. 混音 ✅

- 支持叠加第二条音轨同时发声，两轨播放位置各自独立。
- **绝对不能修改原始音频文件**（版权）。混音只在播放链路里做。

## 7. 已实现后又整体删除的功能 ✅

**蒙版音频律动**（蒙版跟着音乐波动）。

用户原话：*"这个律动效果说实话和我预想的差不少，如果这个功能的资源消耗大、占比大，
那就删。我们之后可能会换其他实现方式。"* 以及 *"呼吸是依赖 WGL 实现的吗？是就一起删，
放个静态模板就行。"*

- 实测代价：开启时 CPU 38.6%，关闭 27.8%，约 11 个百分点。
- 已删除：逐帧时钟驱动、频谱包络上传、`audio/analyser.ts`、着色器里的 `uBands`/`uWaveAmp`。
- 蒙版改为**静态形状**，只在参数变化时画一帧。
- 保留着色器而不是换成静态 PNG——边缘、羽化、蜿蜒、颜色四个参数还要能调，三色取色
  也靠改颜色参数生效。

> 定位：不是"做失败了"，是**换实现方式前的主动下线**。以后要重做律动，从这里接。

## 8. 音源（在线播放）✅ 已落地，界面待补

用户最初的诉求是：*"不要导入歌单功能，先不支持这个功能，导入音源，能够搜索歌曲，听歌就行。"*
2026-08-19 用户改口，歌单导入也要（见 §13）。

**已经跑通的（有实测记录，不是推测）：**

| 环节 | 实现 | 状态 |
| --- | --- | --- |
| 搜索 | 洛雪 musicSdk 原样引入（`src/vendor/lx-music/`），五平台 | ✅ 酷我/酷狗/QQ/网易云/咪咕都有真实结果 |
| 播放地址 | 音源脚本跑在 Worker 里，请求由主线程经 plugin-http 代发 | ✅ 内置「全豆要聚合音源 v9.3」，随应用启动自动启用 |
| 换源 | 本平台解析不出就拿歌名+歌手去别的平台找同一首 | ✅ 五个平台里有三个只有靠换源才通 |
| 地址验证 | 拿到地址先用 Range 请求确认 Content-Type 是音频 | ✅ 挡掉了酷狗那种「返回 200 但内容是 JSON」的假地址 |
| 播放 | 整段取回成 Blob 再播，不直连流式 | ✅ 实测 3.59MB / 514ms，解码时长 309.5s，能播 |
| 歌词 | musicSdk 自带，**不经过音源脚本** | ✅ 网易云/酷狗/酷我出完整逐字歌词；QQ 与咪咕靠换源 |
| 封面 | musicSdk 自带 | ✅ 五平台都有 |
| 界面 | — | ❌ **完全没有**。目前只有 `window.__source` 能调到 |

**两条不得不接受的限制：**

1. **QQ 的逐字歌词解不了。** 上游用的是一个作者不公开算法的 C++ 原生插件
   （`qrc_decode.node`），没有源码可移植。已改为换到网易云/酷狗取同一首歌的歌词。
2. **音源脚本寿命以周计。** 用户手上原有的四份（野草/野花/六音/Huibq）在 2026-08-19
   实测已全部失效。因此内置一份能用的，同时保留「导入音源」这条路。判据用
   `npm run probe:source`，它不经过本应用，能分清是音源挂了还是我们接错了。

~~"本播放器作为洛雪的可视化前端"~~ —— 这条方案作废，不需要了。

## 10. 性能与内存 ⏸

用户反馈：*"资源占用反而比之前高了 200 兆，之前大概都是 500 兆左右的波动，现在就是
700 兆 750 兆。"*

用户决定：*"算了吧，暂时就这样吧。之后我打算重播的时候再来做，优化内存。"*

**已搁置**，重做播放链路时一并处理。相关已知数据：

| 项 | 实测 | 目标 |
| --- | --- | --- |
| 空闲内存 | 392MB | < 350MB |
| 播放峰值 | 810MB（强制 GC 后回落 547MB，说明是未回收垃圾不是泄漏） | < 550MB |
| 导入 1000 首 | 50.2s（并发 2），峰值 701MB | < 15s |
| 安装包体积 | 2.44MB | < 20MB ✅ |

> 注：323MB 是 Chromium 空白页的地板，与本项目代码无关。

## 12. 工作方式约束

用户对协作方式的明确要求：

- **一次一个任务，独立提交，独立报告，到点即停。**
- 批量执行时不要反复确认：*"你分批做完吧，不用反复和我确认。做完我直接来测试。"*
- **不能动用户自己开的进程。** 测量脚本只能操作自己启动的进程，按 PID 树精确回收。
- 测试用正常长度的音频（3–5 分钟），不要造 60 分钟的文件。
- 不要在亮度、裁切尺寸这类细节上过度纠结。

## 14. 下一步（2026-08-19 重排）

用户明确要求：先把「正统音乐软件的基础功能」补齐，其中**主流平台的歌单/收藏歌单导入**是加分项。

### 已验证可行的（实测，不是设计推演）

**歌单导入**：musicSdk 每个平台都带 `songList.getListDetail` 和分享链接解析正则。
拿真实歌单跑的结果：

| 平台 | 结果 |
| --- | --- |
| 网易云 | ✅ 歌单 id 与分享链接都行，《热歌榜》200 首 |
| QQ 音乐 | ✅《晨跑活力站》35 首 |
| 酷我 | ✅《不知道》103 首 |
| 酷狗 | ✅ 分享链接可以，裸 specialId 不行 |
| 咪咕 | ⚠️ 部分 id 报错，SDK 这块比较脆 |

用户自己的"我喜欢的音乐"就是一个歌单，**只要不是私密的，贴分享链接就能导**。
歌单只给曲目信息不给播放地址，所以要做成**播到哪首解析哪首**，不能一次性全解析。

### 按依赖顺序排

1. **在线曲目与本地曲目的统一模型** —— 地基。现在 `Track` 是围绕 `FileRef` 建的，
   在线曲目进不了播放队列、歌单、收藏、播放统计。不先做它，后面每一项都要返工。
2. **搜索界面** —— 平台切换 + 结果列表 + 播放/加入歌单。
3. **歌单导入** —— 贴链接导入，见上。
4. **音量归一化（ReplayGain / EBU R128）** —— PRD F7.4 列了但没实现。
   不同专辑母带响度能差 10dB 以上，没有它就是换首歌音量跳一档。
5. **预加载下一首** —— PRD F1.6 要求切歌 < 200ms，现在是切歌那一刻才开始读文件。
6. 组件位置自定义（§4.3，早先已批准未开始）。
7. 内存优化（§10，用户指定在重做播放链路时一起做）。

### 待查

**播放时音量自己起伏**（用户 2026-08-19 报，确认是**同一首歌播放过程中**，不是换歌）。
已排除：不是流式缓冲（本地文件整段读进内存再播，全程不联网）；不是倍速时间拉伸
（`speed: 1`）；不是均衡器（`eqEnabled: false`）；不是混音叠轨（`layers: []`）。
稳定播放期间代码里没有任何一处会改增益。下一步要在播放链路上挂分析节点实测输出包络，
以区分「应用内」还是「应用下游（Windows 响度均衡 / 驱动）」。
